# 蓝牙协议

简体中文 · [English](protocol.en.md)

MideaBar 通过低功耗蓝牙直连美的 / 华凌空调，不需要配对、账号或手机 App。本文描述 App 实际使用的协议：

- 字节层（帧、加密、握手、家电帧）在 [`Sources/MideaProtocol`](../Sources/MideaProtocol)，纯算法、不依赖蓝牙，有单元测试（`make test`）。
- 蓝牙与时序（扫描、连接、重发、重连）在 [`Sources/MideaBar/ACLink.swift`](../Sources/MideaBar/ACLink.swift)。

协议来自对设备行为的公开研究，参考了 [midea-ble-go](https://github.com/midea-ble/midea-ble-go)；单元测试里的一致性向量取自它的输出。

## 1. 发现设备

空调持续广播厂商数据，厂商 ID 为 `0x06A8`。去掉 2 字节厂商 ID 后：

```
01 | SN（14 字节 ASCII）| 01 03 00 32 | MAC（6 字节）| 00
```

广播可能分包发出，**收到 ≥25 字节的完整包**才能拿到 MAC。macOS 不暴露设备真实 MAC，握手所需的标识只能从这里重建：

```
advertisData = 0xAC ‖ SN 前 8 字节 ‖ MAC（倒序）     共 15 字节
```

App 扫描 8 秒：看到上次连过的 SN 立即连接，否则选信号最强的一台。

## 2. GATT

| 项 | UUID | 说明 |
|---|---|---|
| 服务 | `FFA0` | |
| 写特征 | `FFA1` | **只接受带回执的写入**，无回执写入会被静默丢弃 |
| 通知特征 | `FFA2` | 回包可能分片或粘包，按连接层帧头 `AA 55` 和长度重组 |

## 3. 三层帧

外发：家电帧 → 业务层 → 安全层（加密）→ 连接层 → 写入 `FFA1`；接收反之。

| 层 | 格式 | 校验 |
|---|---|---|
| 连接层 | `AA 55 LEN SEQ TYPE body CHK`，`LEN = body + 4` | `CHK = -Σ(LEN..body) & 0xFF` |
| 安全层 | `CMD SEQ LEN body` | 无，由 AES-CCM 的 tag 保证 |
| 业务层 | `TYPE LEN 00 body CHK`，`TYPE` 恒为 `0x20` | `CHK = -Σ(TYPE..body) & 0xFF` |

- 连接层 `TYPE`：`02` = 内含 rootKey 加密的握手帧，`03` = 内含 sessionKey 加密的业务帧。
- 安全层 `CMD`：`01`~`03` 为握手 c1~c3，`04` 为业务。
- 两层的 `SEQ` 各自独立，初始随机 1~255，每发一帧 +1（跳过 0）。
- 连接层 body 短于 16 字节时不是密文，而是设备错误码，如 `ff04`（安全层处理失败）、`ff05`（计数错误）。

## 4. 密钥与加密

```
rootKey    = HKDF-SHA256(ikm = advertisData, salt = 空, info = "midea_bleapp")，取 16 字节
sessionKey = SHA-256(P-256 ECDH 共享点的 X 坐标)，取前 16 字节
```

公钥均为 64 字节 `X ‖ Y`（去掉 `0x04` 前缀）。

加密是 **AES-128-CCM**：8 字节随机 nonce、8 字节 tag、无附加数据，密文格式为 `nonce ‖ 密文 ‖ tag`。CryptoKit 不提供 CCM，App 按 RFC 3610 用 AES 分组加密组合 CBC-MAC 与 CTR 实现。

## 5. 握手

```
App                                               空调
 │  c1：6 字节随机 openId（rootKey 加密）            │
 │ ────────────────────────────────────────────────→│
 │←──────────────────────────────────── c1 应答      │
 │  c2：空内容（rootKey 加密）                       │
 │ ────────────────────────────────────────────────→│
 │←─────────────────────── c2 应答：设备临时公钥     │
 │  生成 P-256 密钥对，算出 sessionKey               │
 │  c3：我方公钥 ‖ sessionKey 加密的 advertisData    │
 │ ────────────────────────────────────────────────→│
 │←──────────────────── c3 应答：1 成功 / 0 失败     │
 │  业务帧（sessionKey 加密）……                      │
```

时序要点：

- **c1 反复发**：设备常忽略新连接的前一两个 c1。每 1.5 秒发一个全新的帧（新序号、新 nonce），最多 15 次。
- **c2 不能多算**：设备每收到一个 c2 就轮换临时密钥。c2、c3 阶段重发的必须是同一帧，每 1.2 秒一次，最多 8 次；收到公钥后立即发 c3，否则设备几秒后会断开。
- 每次连接都重新完整握手，整个握手 30 秒超时。

## 6. 家电帧

业务层 body 是标准美的家电帧（设备类型 `0xAC`）：

```
AA LEN AC 00 00 00 00 00 PROTO MSG OPCODE 数据… CRC8 SUM
```

- `CRC8`：CRC-8/MAXIM（反射多项式 0x8C），覆盖从 `OPCODE` 起的数据段。
- `SUM`：`-Σ(LEN..CRC8) & 0xFF`。

| 帧 | OPCODE | 长度 |
|---|---|---|
| 控制 | `0x40` | 37 字节，`PROTO=2 MSG=2` |
| 查询 | `0x41` | 24 字节，`PROTO=0 MSG=3` |
| 状态回包 | `0xC0` | 设备应答或主动推送 |

### 控制帧（0x40）主要字段

| 字节 | 字段 |
|---|---|
| 11 | bit0 开关机、bit1 控制来源（恒 1）、bit6 蜂鸣 |
| 12 | bit5-7 模式（1 自动 2 制冷 3 除湿 4 制热 5 送风）、bit0-3 温度整数 − 16、bit4 半度 |
| 13 | 风速：40 低 / 60 中 / 80 高 / 100 强风 / 102 自动 |
| 17 | 扫风：基值 `0x30`，上下 `0x0C`，左右 `0x03` |
| 18 | bit5 强劲 |
| 19 | bit3 电辅热、bit7 节能 |
| 28 | 第二温控：`(round(t×10 + 0.5) / 10 − 12) & 31` |
| 34 | 帧序号 1~255 循环 |

定时、睡眠曲线等未使用的字段按协议默认值编码。**控制是「读-改-写」**：先把设备状态灌入，再改目标字段，整帧下发，避免把没改的设置冲掉。

### 状态回包（0xC0）主要字段

记 `S = 帧[10…]`（`S[0] = 0xC0`）：

| 位置 | 字段 |
|---|---|
| S[1] | bit0 开关机、bit7 故障 |
| S[2] | bit5-7 模式、bit0-3 温度整数 − 16、bit4 半度 |
| S[3] | 风速 |
| S[7] | 高 4 位为 `0x3` 时，低 4 位为扫风（`0x0C` 上下、`0x03` 左右） |
| S[8] | bit5 强劲 |
| S[9] | bit3 电辅热、bit4 节能 |
| S[11] / S[12] | 室内 / 室外温度 `(x − 50) / 2`，小数位分别在 S[15] 的低 / 高半字节 |
| S[13] | 第二温控 − 12 |

## 7. 业务收发

- 命令串行执行，以收到任意一条状态回包作为应答（设备也会主动推送状态）。
- 设备常丢第一帧，且对连续的帧去抖约 550ms 再回复。所以发出后 0.15 秒补发一次，之后每秒重发，最多 6 次；重发内容不变，只换序号。
- 没有应答、连接断开或握手失败时断开并在 5 秒后重连。

## 8. 安全性

rootKey 完全由公开广播推出，附近任何人都能算出来；会话密钥只能防住被动偷听，防不住在握手时冒充一方的主动攻击。也就是说，蓝牙范围内（约十米）的人有能力控制你的空调。家用场景问题不大，但应当知道。
